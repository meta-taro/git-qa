# ADR 0003 — 端末の映像をどこから取り出すか（未決）

- 状態: **暫定で B を採用**（2026-09-02・実測で成立を確認）。**A へ戻る余地は残す**
- 日付: 2026-09-02
- 関連: C4（ライブビューが主媒体）/ C27（方式 A ＋ Tauri）/ PRD §2 / Issue 004 / Issue 005

## 何が決まっていて、何が決まっていないか

**決まっている**（ADR 0002 / C27）

- 映像は**アプリの枠の中で自前で描く**（方式 A）。別窓を並べない
- 受け手（生 H.264 を切って WebCodecs で復号して canvas に描く）は**実装済みで検査済み**
  （`packages/desktop/src/live/`）

**決まっていない**

> **その生 H.264 を、どこから取り出すか。**

## 選択肢

| | 取り出し方 | 良い所 | 引っかかる所 |
|---|---|---|---|
| **A. scrcpy のサーバへ直接繋ぐ** | `scrcpy-server.jar` を端末へ push し、adb のソケットから生 H.264 を受ける | scrcpy と同じ低遅延。**PRD §2 の「scrcpy 前提」に沿う** | **scrcpy のクライアント側を自分で書くことになる。**非目標「scrcpy の再実装」に近づく。scrcpy 側の protocol は版で変わる |
| **B. `adb exec-out screenrecord --output-format=h264 -`** | Android 標準の `screenrecord` が生 H.264 を標準出力へ吐く | **追加の依存が無い**（adb だけ）。実装が薄い | **遅延が scrcpy より大きい**（未実測）。**1 回 180 秒の上限**があり、繋ぎ直しが要る |
| C. scrcpy を別窓で出したまま | いま Android アダプタがやっていること | 実装済み | **C4 と噛み合わない。**人が 2 つの窓を見比べることになる |

## なぜ AI の判断だけで決めないか

**PRD §2 が「Android — scrcpy 前提（低遅延）」と明記している**（product-baseline §15：
記録済みの決定を AI の判断だけで覆さない）。B を採ると、その前提を変えることになる。

一方で**非目標に「scrcpy の再実装」が挙がっている**（PRD §11）。A は、そこへ近づく。

**この 2 つが正面から当たっている。**どちらを取るかは、製品が何を大事にするかの判断で、
実装の都合ではない。

## 決める前に測れること（提案）

**B を先に実装して遅延を測るのが安い。**追加の依存が無く、`screenrecord` は数十行で繋がる。

- 測った遅延が Issue 005 の上限に収まる → **B で足りる。**A を書かなくてよい
- 収まらない → **A へ進む根拠が実測で出る。**「scrcpy の再実装」を非目標から外す判断も、
  そのとき数字を持って出せる

**180 秒の上限は、ケースの区切りで繋ぎ直せば実用上は問題にならない**見込み（1 ケースは
それより短い）。ただしこれも未実測。

## 決定（2026-09-02）

**B を採る。**まず実装して測る、という方針どおり実装し、**エミュレータで成立を確認した。**

`--output-format=h264` は `screenrecord --help` に載っていない（AOSP の隠しオプション）。
**実際に叩いて確認した。**

```
$ adb exec-out screenrecord --output-format=h264 --time-limit=5 -
00000000: 0000 0001 6742 c032 8d68 0440 117e 5b90
          ^^^^^^^^^ ^^
          開始コード  NAL type 7（SPS）
```

### 実測（Pixel 3a / API 31 のエミュレータ・操作を流しながら）

| | 値 |
|---|---|
| 受け取り | 1,216,253 バイト / **32 枚**（アクセスユニット）/ 4,793 ms |
| **最初の 1 枚まで** | **491 ms** |
| 実効ビットレート | 約 2.0 Mbps（`screenrecord` の既定の上限は 20 Mbps） |

`adb` → 生 Annex-B → `createAnnexBSplitter` → **IDR を含む枚**、まで一本で通った。
検査は `packages/adapter-android/test/device.e2e.test.ts`（`GIT_QA_ANDROID_E2E=1` で走る）。

**画面が変化しないとフレームが出ない。**静止した画面では 10 秒で 2 枚しか出なかった。
scrcpy と同じ性質で、**容量は実時間ではなく画面が変化した量に比例する**（Issue 007 の実測と一致）。

### まだ言えていないこと

- **「最初の 1 枚まで 491 ms」は遅延そのものではない。**測ったのは繋いでから絵が出るまでで、
  **「操作してから画面に出るまで」ではない**。それは Issue 005 で測る
- **エミュレータであって実機ではない。**実機の `screenrecord` はこれより遅い / 速い可能性がある
- **180 秒の上限を跨ぐ繋ぎ直しを実装していない。**1 ケースがそれより長い運用では要る

### 見つかった穴 — codec 文字列が固定になっている

`webcodecs.ts` の `CODEC` は `avc1.42E01E`（Baseline / Level 3.0）で固定。
**端末が実際に吐いた SPS は `42 c0 32` ＝ Baseline / Level 5.0** だった（1080x2220 なので当然）。

復号器は Annex-B のとき level をあまり見ないので実害は出ていないが、
**本来は SPS から組み立てるべき。**端末ごとに変わる。

## A へ戻る条件

- Issue 005 で測った**操作から表示までの遅延が上限を超えた**とき
- 実機で `--output-format=h264` が通らない端末が出たとき（隠しオプションなので保証が無い）
- 180 秒ごとの繋ぎ直しが、実運用で目に見える切れ目になったとき
