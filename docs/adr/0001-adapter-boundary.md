# ADR 0001 — Adapter の境界

- 状態: 採用（2026-08-17）
- 関係する決定: C4（ライブビューが主媒体）/ C8（Adapter に入る条件）/ C11・C20（録画）/ C19（機体は run.json 側）
- 出典 Issue: `.claude/issues/002-adapter-boundary.md`

## 決めたこと

対象（Android / Web / デスクトップ）を扱う口を `TargetAdapter` として定義した。実体は `packages/core/src/adapter/`。

1. **ライブ映像を出せることを、型として必須にした。**`TargetSession.liveView` は省略できない。
2. **画面の状態は共通の型へ潰さず、対象ごとの生データをそのまま渡す**（`Observation.raw: unknown`）。
3. **`target`（機体・ビルド）はアダプタが作り、run.json へそのまま入る。**コア側で組み直さない。
4. **録画の結果は `CaseRecording` の 4 状態をそのまま返す。**アダプタ独自の戻り値を作らない。
5. 接続先の指定（起動 URL・パッケージ名・実行ファイル）は**インターフェースに持たせない。**アダプタを作るときの引数として、実装ごとに受ける。

## なぜそうしたか

### 1. ライブビューを必須にした

C8 の線引き「ライブ映像を出せるものが Adapter に入る」を、文書だけに書いても守られない。任意にすると、映像を出せない対象（API・CLI・バッチ）が「実装しなければいいだけ」で入ってくる。**入れられない形にするのが唯一効く。**C17（結果の語彙を型で分けた）と同じやり方。

この道具は「人が横で見て保証する」ことが芯なので、見るものが無い対象は、そもそも保証の対象にならない。

### 2. 生データを素通しにした

Web の DOM、Android のアクセシビリティツリー、デスクトップの UI Automation は、**同じものの方言ではなく別物**。共通の木に潰すと、潰した時点で情報が落ちる。落ちた情報は、後から「なぜ AI がそう判断したか」を追うときに要る。

コアは `raw` を読まない。読むのは、その形を知っている側（アダプタ自身、あるいは人）。

代わりに、何が取れるかは `capabilities.observation` に**名前だけ**持たせた（`dom` / `accessibility-tree` / `ui-automation` / `none`）。名前だけなら対象を足しても壊れない。

### 3. `target` をアダプタが作る

コア側で `target` を組み直すと、**実際に繋いだ相手と、証跡に書いた相手がずれても誰も気づけない。**繋いだ本人に書かせる。契約テストで `validateRun` に通るところまで確かめている。

### 4. 接続先をインターフェースに持たせない

「どこへ繋ぐか」は対象ごとに形が違いすぎる（URL / パッケージ名 + Activity / 実行ファイルのパス）。共通の型にすると、どの対象でも半分しか埋まらない構造体になる。`createXxxAdapter(options)` の引数として実装ごとに受ければ、コアは知らなくて済む。

## Web を当ててみた結果（実装はしない・Phase 5 で判断）

Issue 002 の作業 3。**インターフェースの形だけを当てて、過不足を出した。**

### 余るもの

| もの | Web では |
|---|---|
| `Action.swipe` | 使うのはタッチをエミュレートするときだけ。通常は要らない |
| `PointerRef.at: 'point'` | 座標指定はスクロール位置に依存するので実用しにくい。`at: 'element'` だけで足りる |
| `Target.device` / `osVersion` | ブラウザ名・版のほう（`Target.browser`）が要る。すでに任意なので害はない |

余る分は **害が小さい**（使わなければよい）。減らすと Android 側が困るので、このままにする。

### 足りないもの

| もの | なぜ要るか | 今どうするか |
|---|---|---|
| **画面遷移（URL を開く）** | Android の起動 intent に相当する操作が `Action` に無い | 接続時の引数で「最初にどこを開くか」を受ける。検証中の遷移は、画面上の操作で行う |
| 待つ（描画・通信の完了） | Web は特に待ちが要る | `observe()` を繰り返して待つ。専用の口は作らない |
| タブ / ウィンドウ / フレームの切り替え | Web 固有 | 未定。Phase 5 で要否を判断する |
| スクロール | `swipe` で表せるが、Web は wheel のほうが自然 | `swipe` で代用する |

**いま足さない。**使う対象が無いまま口を増やすと、Android 実装が満たせない約束だけが増える（Issue 002 の注意「対象を増やすことを目的にしない」）。

Phase 5 で Web を足すときに**コア側の変更が要ったら、この設計が間違っていた**ということ。その判定ができるように、ここに書き残す。

## 代わりに考えて採らなかった案

| 案 | 採らない理由 |
|---|---|
| 画面の状態を共通の木（要素・座標・テキスト）へ正規化する | 正規化した時点で情報が落ちる。落ちたことに後から気づけない |
| ライブビューを任意にして、対応しない対象も Adapter に入れる | C8 の線引きが実質無くなる。API / CLI が入ると「人が見て保証する」前提が崩れる |
| 録画をアダプタ独自の型で返し、コア側で `CaseRecording` へ変換する | 変換の途中で「録画オフ」と「録画失敗」が潰れる余地ができる（C20 が防ごうとしたもの） |
| 接続先を共通の型（`{url?, package?, path?}`）で持つ | どの対象でも半分しか埋まらない。埋まっていない理由が読めなくなる |

## テスト用アダプタを `packages/core` に同梱する

`createFakeAdapter()` は本番の実行では使わないが、**core から輸出している。**

実機・adb が無くても、この道具の芯（人が見て保証する流れ）を通しで動かせるようにするため。下流のパッケージ（実行器・デスクトップ）が対象なしでテストを書くのにも要る。

契約テスト `packages/core/test/adapter/contract.ts` は**実装ごとに当てる束**として書いてある。Android を作るとき・Web を足すときは、これを通すことが答え合わせになる。

## まだできていないこと

- **Android 実装は無い。**adb + scrcpy と実機が手元に無いため（Issue 001 / 004 / 005 と同じ理由で止まっている）。**Issue 002 の完了条件「Android 実装がそのインターフェースを満たしている」は未達**であり、この ADR はインターフェースの決定だけを記録している。
- `Target.kind` に `ios` は無い。Issue 001（Windows から iOS のライブ映像が出せるか）の結果が出るまで足さない。
