# AI時代の製品開発・人間中心UXチェックリスト

> **これは何か**
>
> 製品の品質チェックに使う判断基準です。設計書でも仕様書でもありません。
> **答えられない問いがあること自体が結果**で、埋まらない欄を空のまま残して構いません。
>
> **いつ開くか** — 企画を始めるとき（§0）／作り始める前（§1〜§14）／出す前（§15）。
> 毎日つけるものではありません。
>
> **誰が書くか** — **その製品を使う人を見た人間が書きます。** AI に代筆させると、
> 「観察したか」を問う欄が観察していないまま埋まります（§12 が丸ごと無意味になります）。
> AI に頼んでよいのは、書いた答えへの反論と、抜けている観点の指摘です。

## 0. Product Gate ― 最初に確認する5問

詳細設計に入る前に、最低限この5問に答える。

- [ ] **人はなぜこれを使いたいのか？**
- [ ] **人はなぜ今の方法をやめて、これを使うのか？**
- [ ] **自動化によって「良い面倒」まで消していないか？**
- [ ] **人はなぜこれにお金を払うのか？**
- [ ] **AIが10倍賢くなっても、この製品は必要か？**

### 判定

5問に明確な回答ができない場合、

> **「技術的には作れるが、製品として成立するかは未検証」**

として、一度企画を止める。

### OSS はここで問いが分岐する

**4問目「人はなぜこれにお金を払うのか？」は、OSS では問わない。**
無償で配るものに支払いの問いを当てると、成立するはずの企画がここで止まる。

代わりに、**同じ場所で別の問いを当てる。**

- [ ] **作った人がいなくなっても、これは続くか？**

支払いの問いが確かめていたのは金額ではなく、
**その製品を必要としている人が、作者の外にいるか**である。
OSS ではそれが「引き継げるか」の形で現れる。次の 3 つが揃っていれば答えられる。

- [ ] 手元に落として自分でビルドし、自分で公開できる（作者の環境や鍵に依存しない）
- [ ] この製品が終了しても、生み出したデータ・成果物は他所で読める
- [ ] 仕様・様式が製品と分離していて、実装が消えても残る

**3 つとも書けないなら、OSS でも一度止める。**
「無償だから誰も損しない」は、続かない企画を通す理由にはならない。
続かなかったとき損をするのは、それを前提に何かを作った人である。

**残り 4 問（使いたいか／今の方法をやめるか／良い面倒を消していないか／
AI が 10 倍賢くなっても必要か）は、OSS でも商用でも同じように問う。**
ここを緩めると、作りたいから作っただけのものが通る。

# 1. そもそも人はこれを欲しがるか

- [ ] 技術ではなく、ユーザーの欲求から製品を説明できる
- [ ] 「AIだから」を除いても価値を説明できる
- [ ] 「自動化できるから」を除いても価値を説明できる
- [ ] ユーザーが現在行っている具体的な行動と接続している
- [ ] 「便利になる」ではなく「何が嬉しくなるのか」を説明できる
- [ ] 開発者自身の課題を、一般ユーザーの課題だと思い込んでいない
- [ ] ユーザーがお金・時間・手間のいずれかを投入するほどの価値がある
- [ ] 「あれば便利」ではなく「使いたい」と思える理由がある

---

# 2. 人間の「面倒」を正しく分類したか

すべての面倒をなくせば良いわけではない。

## 悪い面倒

ユーザーが価値を感じていない摩擦。

例：

- 転記
- 重複入力
- 不必要な待ち時間
- ファイル変換
- 定型処理
- 大量の検索
- データ整理
- 同じ操作の繰り返し

これは積極的にAI・ソフトウェアで削減する。

## 良い面倒

行為そのものが体験価値になっているもの。

例：

- 選ぶ
- 考える
- 比較する
- 試す
- 相談する
- 工夫する
- 作る
- 達成する
- 発見する

これは安易に自動化しない。

### Checklist

- [ ] 消そうとしている手間をユーザー自身が嫌っているか
- [ ] その手間自体が楽しさになっていないか
- [ ] 選択する楽しみを奪っていないか
- [ ] 考える楽しみを奪っていないか
- [ ] 達成感を奪っていないか
- [ ] 発見する楽しみを奪っていないか
- [ ] コミュニケーションのきっかけを消していないか
- [ ] 効率化した結果、製品がつまらなくならないか

> **非効率の中には「体験」「納得」「遊び」「自己決定」が含まれている。**

---

# 3. 人間を製品から追い出しすぎていないか

AIに任せられることと、AIに任せるべきことは違う。

- [ ] ユーザーが自分で決める場所が残っている
- [ ] AIが勝手に重要な意思決定をしていない
- [ ] 必要な場面では確認・承認を挟める
- [ ] AIの提案を修正できる
- [ ] AIの提案を拒否できる
- [ ] AIに任せる範囲をユーザー自身が決められる
- [ ] 初心者と熟練者で自動化レベルを変更できる
- [ ] 「全部自動」が本当に最良なのか検討した
- [ ] 人間が介入することで価値が増える場所を残している

> **Automation Level ≠ Product Quality**

自動化率が高いことは、それ自体では製品価値ではない。

---

# 4. 人間の時間感覚に合っているか

AIでは「速ければ速いほど良い」という思い込みが起こりやすい。

- [ ] 即時性が本当に価値になる処理か
- [ ] あえて考える時間を残した方がよくないか
- [ ] 結果を段階的に見せた方が理解しやすくないか
- [ ] 処理中であることが分かるか
- [ ] 完了したことが明確に分かるか
- [ ] ユーザーが置いていかれない速度になっているか
- [ ] 待ち時間をなくすこと自体が目的になっていないか
- [ ] 過程を見ることに価値がないか

---

# 5. 「理解できる」が設計されているか

高性能でも、理解不能な製品は使われにくい。

- [ ] 今何が起きているか分かる
- [ ] AIが何をしているか分かる
- [ ] AIが何をしたか後から確認できる
- [ ] 必要な場合、その判断理由を確認できる
- [ ] 次に何をすればいいか分かる
- [ ] 間違った場合の戻し方が分かる
- [ ] 専門用語を知らなくても主要機能を利用できる
- [ ] AIの状態と人間が操作すべき状態を区別できる
- [ ] 完了・失敗・保留・確認待ちが明確に区別されている

---

# 6. 「安心して失敗できる」か

AI製品では、賢さと同じくらい「戻せること」が重要になる。

- [ ] Undoできる
- [ ] Previewできる
- [ ] 履歴を確認できる
- [ ] AIによる変更箇所を確認できる
- [ ] 重要操作には確認がある
- [ ] 間違えても致命傷にならない
- [ ] 元の状態へ戻せる
- [ ] 自動保存・バックアップが適切に存在する
- [ ] 「触ったら壊れそう」という心理を作っていない
- [ ] AIが失敗することを前提として設計されている

> **AIの精度を100%に近づけることだけでなく、間違っても困らないシステムを作る。**

---

# 7. 人間関係・社会的行動を考慮したか

製品は単独の人間だけで使われるとは限らない。

- [ ] 誰が使う製品なのか定義されている
- [ ] 誰と一緒に使うのか考えている
- [ ] 他人に見せる場面を考えている
- [ ] 共有しやすい
- [ ] 他人に説明しやすい
- [ ] 上司・同僚・顧客・家族など第三者を考慮している
- [ ] 利用者と意思決定者が違う可能性を考慮している
- [ ] 利用者と支払者が違う可能性を考慮している
- [ ] AIによって既存のコミュニケーションを不必要に破壊していない
- [ ] 製品を使うこと自体が恥ずかしい・面倒と思われない

---

# 8. 「使い始める理由」があるか

価値があっても導入されなければ存在しないのと同じ。

- [ ] 最初の価値体験までが短い
- [ ] 登録前に価値を理解できる
- [ ] 初期設定が価値に対して重すぎない
- [ ] データ移行が障壁にならない
- [ ] 新しい習慣を大量に要求しない
- [ ] 現在の仕事・生活の流れに差し込める
- [ ] 今使っている製品から移行する理由がある
- [ ] 「あとで試そう」で終わる構造になっていない
- [ ] 初回利用時に成功体験を作れる

---

# 9. 「使い続ける理由」があるか

購入されることと、使われることは違う。

- [ ] 2回目に使う理由がある
- [ ] 1週間後にも価値がある
- [ ] 1か月後にも価値がある
- [ ] 継続するほど便利になる
- [ ] ユーザーのデータが価値として蓄積する
- [ ] 履歴が価値として蓄積する
- [ ] 設定が価値として蓄積する
- [ ] 学習結果が価値として蓄積する
- [ ] 毎回同じ面倒な設定を要求しない
- [ ] 製品を思い出す自然なトリガーが存在する
- [ ] 「習慣」の中に入れる可能性がある

---

# 10. お金を払う瞬間を設計したか

利用価値と経済価値は別々に検証する。

> **OSS はこの章を飛ばしてよい。**代わりに章末の「OSS の場合」を埋める。
> 支払いの節を無理に埋めると、寄付・スポンサー・有償版といった
> **やる気のない答え**が並び、それが企画書に残って後から本当のことのように読まれる。

- [ ] 誰がお金を払うのか明確
- [ ] なぜお金を払うのか明確
- [ ] 利用者と支払者が違う場合を考慮している
- [ ] 無料版だけで十分になってしまわない
- [ ] 課金によって得られる価値を一文で説明できる
- [ ] 料金体系を簡単に理解できる
- [ ] 料金を理解するために複雑な計算を要求しない
- [ ] 支払う瞬間までに価値を体験できている
- [ ] 価格と得られる価値を比較できる
- [ ] 解約しづらくするのではなく、継続したくなる価値を作っている

## OSS の場合 ― 「払う人」ではなく「引き継ぐ人」を設計したか

- [ ] 手元に落として自分でビルドできる（作者の環境・鍵・アカウントに依存しない）
- [ ] 自分で公開まで到達できる（配布経路が作者個人のものになっていない）
- [ ] この製品が終了しても、生み出したデータ・成果物は他所で読める
- [ ] 仕様・様式が実装から分離していて、実装が消えても残る
- [ ] 使う人が、直したい箇所を自分で直せる大きさ・読みやすさになっている
- [ ] 引き継ぐ人が最初に読むもの（README・設計の記録）が実在する
- [ ] 「作者に聞かないと分からない」ことが機能の中心に無い

> **無償であることは、続くことを意味しない。**
> 続かなかったときに損をするのは、それを前提に何かを作った人である。

# 11. 「性能競争」だけになっていないか

特にAI製品では重要。

- [ ] AIモデルが他社と同等になっても製品価値が残る
- [ ] 「精度が高い」以外の競争力がある
- [ ] 「速い」以外の競争力がある
- [ ] UXに独自性がある
- [ ] ワークフローに組み込まれている
- [ ] ユーザーの習慣に入り込める
- [ ] データ・履歴・設定などが時間とともに価値になる
- [ ] 人間関係・コミュニティなどに接続している
- [ ] 基盤AIを他社も利用できるようになっても存在意義がある

### AI 10倍テスト

> **明日、OpenAI・Google・Anthropic等の基盤AIが10倍賢くなったとして、この製品はまだ必要か？**

- [ ] YES

NOの場合、製品価値ではなく基盤AIの能力そのものを販売している可能性がある。

---

# 12. 人間を実際に観察したか

アンケートだけでは、人間の実際の行動は分からない。

- [ ] 実際にユーザーが作業しているところを見た
- [ ] ユーザーが何に時間を使っているか確認した
- [ ] ユーザーがどこで迷うか確認した
- [ ] ユーザーがどこで諦めるか確認した
- [ ] ユーザー独自の工夫・裏技を観察した
- [ ] 本来想定していなかった使い方を調べた
- [ ] ユーザーが言っていることと実際の行動を分けて考えた
- [ ] 製品以外の行動まで観察した
- [ ] 他人とのコミュニケーションまで観察した
- [ ] なぜ現在の方法を続けているのか確認した

> **AIを見るより、人間を見る。**

人間が合理的に行動すると仮定してUXを設計しない。

---

# 13. 製品そのもの以外の価値を見落としていないか

ファミリーレストランの価値は、料理の味だけではない。

例えば、

- 入りやすい
- 値段が分かる
- メニューを見る楽しみがある
- 誰と行っても困らない
- 長居できる
- 店員との距離感が適切
- 店舗が違っても体験を予測できる

といった価値が存在する。

製品についても同様に確認する。

- [ ] コア機能以外にユーザーが感じている価値を調べた
- [ ] 安心感に価値がないか
- [ ] 選ぶことに価値がないか
- [ ] 所有することに価値がないか
- [ ] 他人と使うことに価値がないか
- [ ] 見せることに価値がないか
- [ ] 会話のきっかけとして価値がないか
- [ ] 過程そのものに価値がないか
- [ ] ブランド・世界観に価値がないか
- [ ] 「いつも同じ」という予測可能性に価値がないか

---

# 14. 効率化によって目的そのものを壊していないか

次の問いを行う。

> **この行為を0秒・0クリック・完全自動にした場合、ユーザーは本当に幸せになるか？**

- [ ] YES

NOの場合、その工程には体験価値が存在する可能性がある。

### 例

旅行：

> 目的地・航空券・ホテル・飲食店をAIが0.1秒ですべて決定・予約する。

技術的には高性能でも、

- 探す
- 比較する
- 想像する
- 誰かと相談する
- 迷う
- 決める

こと自体が旅行体験なら、完全自動化はUXを悪化させる。

ゲーム：

> AIがラスボスを0.1秒で倒す。

性能は高いが、ゲームとしての目的を破壊している。

# 15. 最終Product Gate

リリース・本格開発前に再確認する。

## Human

- [ ] 人間の具体的な欲求に接続している
- [ ] 実際の人間の行動を観察した
- [ ] 良い面倒を残している
- [ ] 自己決定感を残している
- [ ] 理解できる
- [ ] 安心して失敗できる

## Product

- [ ] 最初の価値体験がある
- [ ] 継続利用する理由がある
- [ ] 現在の方法から移行する理由がある
- [ ] コア機能以外の体験価値を設計している

## Business（商用）

- [ ] 誰が払うか分かる
- [ ] なぜ払うか分かる
- [ ] 継続して払う理由がある
- [ ] 多数の人間の行動と接続できる

## Continuity（OSS — 上の Business の代わりに埋める）

- [ ] 作った人がいなくなっても続く形になっている
- [ ] 第三者がビルドから公開まで到達できる
- [ ] 終了しても成果物・データが他所で読める
- [ ] 多数の人間の行動と接続できる

## AI

- [ ] AIを使うこと自体が目的になっていない
- [ ] 不必要な完全自動化をしていない
- [ ] AIの失敗を前提としている
- [ ] AI性能がコモディティ化しても価値が残る
- [ ] AIが10倍賢くなっても製品が必要である

# Product Principle

> ## 良い製品とは、最も高性能な製品ではない。
>
> **人間の行動の中に自然に入り、  
> 人間が価値を感じ、使い続け、対価を支払う製品である。**
>
> AIによって削るべきなのは、  
> **人間が価値を感じていない摩擦。**
>
> 残すべきなのは、  
> **体験・選択・納得・遊び・達成・自己決定。**
>
> **AIが賢くなるほど、人間を見る。**
