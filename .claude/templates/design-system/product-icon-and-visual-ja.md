# 製品アイコンと見た目の系統 — 家族のルール

**AI が新しい製品のアイコンや DESIGN.md を書く前に、必ずこれを読む。**

> **この文書は「決定」ではなく「型と実測の記録」である。**
>
> ここに書いてあるのは、**すでに人が決めた 5 つの製品**（md-business / dbboard /
> dbboard-web / warifu / git-qa）から**実物を測って抽出した共通点**と、
> **次に決めるとき何を人に聞くか**の手順である。
>
> **次の製品の色・形をこの文書から導出しない。**色の方向・トーンは戦略判断であって、
> 決めるのは製品の持ち主である。AI がやってよいのは「候補を実物で出して並べること」と
> 「決まったものを型に沿って実装すること」まで。過去に AI が推論で
> 「深夜利用だからダーク」と断定し、承認済み企画書（白基調）と矛盾したまま
> 配布した事故がある。

---

## 1. これは強制ではない

**守らないと止まる類のものではない。**メーカーがブランドのロゴを何年もかけて
少しずつ揃えていくのと同じで、**適当なタイミングで、無理のない範囲で寄せていく**ためのもの。

そのため各項目に**推奨ランク**を振ってある。

| ランク | 意味 | 外すとき |
|---|---|---|
| **A** — 揃えたい | 新しく作るならここは沿ってほしい。**家族に見えるかどうかがここで決まる** | DESIGN.md に理由を 1 行書けば外してよい |
| **B** — 寄せたい | **次にアイコンを触る機会があれば**寄せる | 何も書かなくてよい |
| **C** — 参考 | 過去の実測と失敗の記録。**基準ではない** | — |
| **権利** | 意匠の話ではなく、配れるかどうかの話 | **外せない**（§8） |

### 直すタイミング

**動いているアイコンを、この文書のために作り直さない。**

- **未着手**（まだ仮のアイコン / テンプレの残骸）→ 作るときに A を全部拾う
- **次に触る機会がある**（版を上げる・別プラットフォームへ出す・作り直す）→ B もそこで拾う
- **もう出ていて特に困っていない** → **そのままでよい**。利用者の Dock で
  見た目が変わることのほうが不利益になる

「揃っていないから直す」ではなく、**「触るついでに寄せる」**。10 年かけて揃えばそれでいい。

## 2. いつ読むか

| 場面 | やること |
|---|---|
| 新しい製品のアイコンを作る | §3 の A を拾う。色と印は §6 の手順で**人に決めてもらう** |
| DESIGN.md を書き始める | §4 の表を見て、**すでに使われている色を避ける** |
| 既存のアイコンを直す | §8 の描き方（スクリプト）に従う。手描き素材を持ち込まない |
| 「他と揃えて」と言われた | 揃えるのは**形**であって色ではない（§3 と §4 は別の軸） |

## 3. 家族の形

**角丸の四角に、白い印を 1 つ。地はベタ 1 色。**

デスクトップアプリが同じ Dock / タスクバーに並ぶので、**輪郭の形が揃っていないと
別々の出所に見える**。逆に形さえ揃えば、色だけで見分けが付く。

| | 項目 | 値 |
|---|---|---|
| **A** | 輪郭 | **角丸の四角**。中に**印を 1 つ**だけ |
| **A** | 地 | **ベタ 1 色**。**グラデーションを使わない**（小さくすると階調は潰れて濁るだけ） |
| **A** | 印の色 | **白**（`#FFFFFF`）が既定。地が淡い色のときだけ濃色にする |
| **B** | 元データ | **1024px 四方の PNG** 1 枚。ここから全サイズを作る |
| **B** | 外周の余白 | **9%**（1024px で 92px）。角丸の外は**透明**。四角を画面いっぱいにしない |
| **B** | 角丸の半径 | **22%**（1024px で 225px）。iOS / macOS の squircle に近い丸み |
| **B** | 印の線幅 | **4.5%**（1024px で 46px）。これより細いと 32px で消える |

数値の出典は `git-qa` の `make-icon.py`（実際に動いている実装）。

### C — 現状の実測（2026-09-03）

| 製品 | 外周余白 | 角丸 | |
|---|---|---|---|
| git-qa | 9.0% | 17.2% | 数値の出典 |
| warifu | 0% | 18.6% | 縁まで塗っている |
| dbboard | 4.3% | 14.8% | 余白が半分 |
| dbboard-web | 2.5% | 14.6% | 同上 |
| md-business | **0%** | **0%** | 真四角のベタ＋白い枠 |
| sshboard | — | — | **未着手**（テンプレの Svelte ロゴが残っている） |

**全員の DESIGN.md が「角丸の四角で家族として揃える」と書いているのに、
数値は 3 軸ともバラバラだった。**寄っているのは概念であって数値ではない、というのが
この文書を書いた理由。**ただしこれを理由に既存を直す作業を起こさない**（§1）。

## 4. 家族の色

**Dock に並んだとき見分けが付くことが条件。**だから色は揃えず、**分化させる。**

| | 項目 | 内容 |
|---|---|---|
| **A** | 見分け | **すでに使われている色から離す**。下の表を先に見る |
| **A** | 由来 | **製品がいちばん強く主張する 1 語**から引く。「なんとなく綺麗だから」で決めない |
| **B** | 同一製品 | **デスクトップ版と Web 版は同じ色にする** |
| **B** | 別軸 | **UI のアクセント色をアイコンの地に機械的に流し込まない** |

### C — すでに使われている色

| 製品 | 地の色 | 由来 |
|---|---|---|
| md-business | `#5B5BD6` | 藍（アクセント色と同じ） |
| dbboard | `#4F46E5` | 藍（ロゴを公式採用） |
| dbboard-web | `#2563EB` | 青（**dbboard と別。本来は揃えるべきだった**） |
| git-qa | `#34D399` | 緑＝「見て、大丈夫だった」 |
| warifu | `#CDB295` | カフェオレ＝割符の木札を載せる地 |

**藍が 2 つ埋まっている。**次に藍を選ぶ理由は薄い。

### アクセント色とアイコンの地は別のもの

warifu が明示している通り（DESIGN.md §4-A）：

> `--accent`（`#5b5bd6`）は UI の「操作できる一点」の色である。
> アイコンは**物**を描いているので、そこから外した。

アイコンが描くのは物、アクセントが指すのは操作。役割が違う。

## 5. 印（中の絵）

**その製品の芯を、形で説明する。**抽象記号やイニシャルにしない。

| | 項目 | 内容 |
|---|---|---|
| **A** | 芯 | **芯を 1 文で言えること。**言えないなら形が決まらない |
| **A** | 固有性 | **同じ分野の他製品と区別が付くこと**。汎用の記号（鍵・盾・チェック単体）に逃げない |
| **A** | 誤読 | **意味していないものを描かない** |
| **A** | 明暗差 | 地と印の明るさの比を**実測して選ぶ**。git-qa は `#34D399` と白で **1.9:1**。文字のコントラスト基準（4.5:1）とは別で、**32px の Dock で形が読めるか**の話 |

### C — 実例

| 製品 | 印 | なぜそれか |
|---|---|---|
| git-qa | 端末の枠の中のチェック | 芯は「端末の画面を人が見て保証する」。**チェックだけだと他の QA ツールと区別が付かない** |
| warifu | 縦長の木の板（割れ目入り） | 芯は「片割れが合うことで相手が確かめられる」。**鍵も錠も盾も出さない**（割符の意味ではない） |
| dbboard | シリンダー | DB そのもの |

## 6. 決める手順

| | 手順 |
|---|---|
| **A** | **1. AI**: 芯の 1 語の候補と、対応する形の案を**実物の画像で 2〜3 案**出す |
| **A** | **2. 人**: 見て選ぶ。「モカ、カフェオレみたい。木の板をイメージ」のような感覚の言葉でよい（warifu はこの一言で決まった） |
| **B** | **3. AI**: 選ばれた方向をスクリプトに落とし、**32px に縮めて確かめてから**出す |
| **B** | **4. AI**: DESIGN.md に**採った理由と捨てた案**を書く。値だけ書かない |

**1 を飛ばして AI が決めてはいけない。**逆に 3〜4 は AI の仕事で、人に手を動かさせない。

## 7. 小さいサイズ

| | 項目 | 内容 |
|---|---|---|
| **A** | 要件 | **32px で読める**こと。Dock / タスクバー / タブがその大きさで出る |
| **B** | 細部 | **閾値で切る。**warifu の木目は「**128px 未満では描かない**」 |
| **B** | 確認 | 縮めて確認するまでを 1 セットにする。1024px だけ見て判断しない |
| **C** | 失敗例 | 模様を行ごとに飛ばして描いたら、warifu で「木目ではなく破線（ミシン目）」に見えた |

## 8. 描き方（実装）

| | 項目 | 内容 |
|---|---|---|
| **権利** | 素材 | **第三者の素材・トレース・ライセンス品を使わない。**OSS なので、他人の権利物が入ると MIT のまま配れなくなる。**これは意匠の話ではないので、推奨ではなく守る** |
| **B** | 描き方 | **スクリプトで描く。**画像編集ソフトの成果物をコミットしない |
| **B** | 置き場 | `src-tauri/icons/make-icon.py`（git-qa）/ `scripts/make-icon.py`（warifu） |
| **B** | 依存 | 足さない（`math` / `struct` / `zlib` だけで PNG は書ける） |

1024px の PNG を 1 枚吐き、そこから Tauri が全サイズを作る:

```
pnpm --filter <パッケージ> exec tauri icon src-tauri/icons/source.png
```

### なぜスクリプトか

- **色や形を変えたいとき、差分が読める**（画像バイナリの差分は読めない）
- **理由をコメントで隣に置ける。**git-qa / warifu はどちらも冒頭に「なぜこの色か」を書いている
- 人が手で描き直す作業が消える

## 9. 画面側の見た目（アイコン以外）

アイコンと違い、**画面の配色は共有している。**md-business の値が事実上の正本で、
warifu はトークン名ごとそのまま引き写している（`--accent` `#5b5bd6` ほか）。

| | 項目 | 内容 |
|---|---|---|
| **A** | 直書き禁止 | **色を直接コードに書かない。**トークン（CSS custom property）から読む。フォールバック付き（`var(--x, #fff)`）も書かない — 片方のテーマの色が焼き付く |
| **A** | 色だけにしない | **色を唯一の手がかりにしてはいけない。**色覚特性のある読み手と白黒のスクリーンショットで読めなくなる。色を使うときは**必ずラベルか形を添える**（dbboard「Colour is never the only mark」） |
| **B** | 配色の出どころ | アクセント / ニュートラル / セマンティックは `md-business/apps/desktop/DESIGN.md` §2 |
| **B** | 明暗 | ライト / ダーク / **OS に従う**（既定）。dbboard ADR-0041 |
| **C** | 例外 | git-qa は「アクセント以外は OS の色を使う」と決めている（OS のコントラスト設定や色覚補助から外れないため）。**独自の配色を抱え込むかは製品ごと** |

## 10. DESIGN.md に書くこと（すべて B）

値の一覧だけの DESIGN.md は、書いた人以外には使えない。次を入れたい。

- [ ] **決めた日と決めた人**（AI が決めたのか人が決めたのかを含む）
- [ ] **採った案と捨てた案、その理由**
- [ ] **実測した数字**（コントラスト比・何 px で確認したか）
- [ ] **この文書を差し戻すべき条件**（warifu §14 の形）
- [ ] **まだ決めていないものは「決めていない」と書く。**先に埋めると、
      実装が「文書に合わせる作業」になる（sshboard がこの形を取っている）

## 11. この文書の更新

- 正本は 1 つ（`templates/design-system/product-icon-and-visual-ja.md`）。
  配布先の `.claude/templates/` にあるものはコピー
- **新しい製品の色が決まったら §4 の表に足す。**足さないと、次の製品が同じ色を選ぶ
- **実測値は測り直して書く。**「揃えたつもり」は §3 の表の通り実際には揃わない
- **ランクは動かしてよい。**A が現場で守れないなら B へ落とす。
  **守られない A を残すほうが、文書全体が読まれなくなるので害が大きい**
