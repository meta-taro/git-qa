# 005 — ライブビューの遅延を実測する

- Phase: 1
- 前提: 004（一本道が通っていること）

## 目的

**遅延がそのまま体験の質になる。**

1〜2 秒遅れると、人には「AI が固まったのか、遅いだけなのか」が分からない。**分からないと人は手を出す。**そうなった時点で、この道具は目的を達していない。

## 決めること（このリポで決めてよい・企画側へ選択肢を投げ返さない）

- 許容できる遅延の上限（**先に決めてから測る**）
- 測り方（実機の画面と PC の画面を同時に撮る、タイムスタンプを重ねる 等）

## 作業内容

1. 上限を先に決めて書く
2. アプリのウィンドウ内に出ているライブビューの遅延を実測する
3. 上限を超えていた場合、原因を切り分ける（scrcpy 自体か / 埋め込み方式か / 描画か）
4. 超えたままなら Issue 003 の埋め込み方式に戻る

## 完了条件

- 実測値がある（1 回ではなく、複数回の分布）
- 上限以内に収まっている。**収まっていない場合、Issue 003 へ差し戻す判断が書かれている**
- **Appium のスクリーンショット連写を使っていないこと**（C4。遅すぎてライブにならない）

## 注意

- 数字が出ないうちに「体感で問題ない」と書かない。**人が待つかどうかを決めるのはこの数字**
- 測るのは「AI の操作が終わってから画面に出るまで」であって、AI の思考時間ではない

## 作業ログ

### 2026-09-02 — 上限を決め、実測した。**遅さの主犯はエミュレータの描画設定だった**

**上限を決めた（Issue の「先に決めてから測る」）**

> **操作から画面に出るまで 200 ms 以下。**超えたら作りを変える。

根拠: 人が「引っかかった」と感じ始めるのが概ね 100〜200 ms。

**きっかけは人の指摘。**「うごくけどちょっと反応遅いです。PC スペックの問題？」

**測ったもの（Pixel 3a / API 31 のエミュレータ・M1 Mac）**

| | ソフトウェア描画（`-no-window` の既定） | **ハードウェア描画（`-gpu host`）** |
|---|---|---|
| 操作 → 映像にデータが出るまで | 642 ms | **136〜173 ms** |
| 操作 → 変化らしいフレーム | **1,142 ms** | **174 / 221 ms**（3 回中 2 回） |

**PC のスペックではなかった**（M1 / 8 コア / 16 GB・CPU はほぼ空き。`adb` の往復は 74〜112 ms）。
**`-no-window` で起こすと GPU が SwiftShader（CPU 描画）になる**のが原因。

```
（前）GLES: ANGLE (Vulkan 1.2.0 (SwiftShader Device (LLVM 10.0.0)), SwiftShader driver-5.0.0)
（後）GLES: Google (Apple), Android Emulator OpenGL ES Translator (Apple M1), OpenGL ES 3.0 (4.1 Metal)
```

**→ エミュレータは必ず `-gpu host` で起こす。**README に書く。

**まだ測っていないもの**

- **canvas に絵が出るまで**（ここまでの数字は adb の出口での値）。橋・切り出し・復号・描画が乗る。
  復号の待ちは 6.6〜17.2 ms と実測済みなので、上乗せは数十 ms の見込み
- **実機での値。**エミュレータの描画は実機とは別物
- `screenrecord` を使い続けるかどうか（ADR 0003）。**200 ms 前後なら据え置き**、
  canvas まで含めて超えるようなら scrcpy のサーバへ繋ぐ側へ移る
