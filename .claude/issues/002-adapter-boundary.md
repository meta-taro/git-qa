# 002 — Adapter の境界を定義する

- Phase: 0
- 前提: 001（iOS が Adapter に入るかがそこで決まる）

## 目的

この製品は、対象（Web / Android / iOS / デスクトップアプリ）が変わってもガワが変わらないことで成立する。**「ついで」で対象を足せるかどうかは、この境界の設計で決まる。**

## 線引きの基準（決定済み・C8）

> **ライブ映像を出せるものが Adapter に入る。**

| 対象 | ライブ映像 | 扱い |
|---|---|---|
| Web | 出せる | Adapter |
| Android | 出せる | Adapter |
| iOS | **Issue 001 の結果次第** | — |
| デスクトップアプリ | 出せる | Adapter |
| API / CLI / バッチ | **出せない** | **Adapter に入れない** |

初期の企画草案 §21 は Phase 8 で API / CLI を同じ枠に足そうとしているが、**同じ Adapter には入らない。**見るものが無い対象では、人が横で見るという前提そのものが成立しない。

## 決めること（このリポで決めてよい・企画側へ選択肢を投げ返さない）

- Adapter が持つ最小のインターフェース
- Adapter が持たないもの（＝コア側が持つもの）の線引き
- 対象ごとの差異を、どこで吸収するか

## 判断材料

Adapter が扱う必要のある操作の見当（過不足はこの Issue で詰める）:

- 接続 / 切断（デバイス・ブラウザ・プロセス）
- **ライブ映像を出す** ← 芯
- 操作する（tap / click / type / swipe）
- 画面の状態を取る（スクリーンショット / DOM / アクセシビリティツリー）
- 記録の開始 / 停止

**状態の取り方が対象ごとに最も違う。**Web は DOM が取れるが、Android / iOS はアクセシビリティツリー、デスクトップアプリはさらに別。ここを共通の型で潰すか、対象ごとの生データをそのまま渡すかが設計の分かれ目。

## 作業内容

1. インターフェースを定義する
2. **Android で実装する**（Phase 1 で実際に使う）
3. Web で**インターフェースだけ**当ててみて、無理が出ないかを確認する（実装はしない）
4. ADR に残す

## 完了条件

- インターフェース定義がコードとして存在する
- Android 実装がそのインターフェースを満たしている
- Web を当てたときに**足りない / 余る**ものが列挙されている
- ADR がある

## 注意

- **Phase 5 で Web / デスクトップを足すとき、コア側を変更せずに済むかがこの Issue の答え合わせになる。**変更が要ったら、ここの設計が間違っていたということ
- 対象を増やすことを目的にしない。**いま作るのは Android だけ**
