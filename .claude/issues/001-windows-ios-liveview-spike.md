# 001 — ★Windows から iOS の画面をライブで見られるか（唯一の未知）

- Phase: 0
- 前提: なし（最初に着手する）
- 優先度: **最高**

## 目的

**この製品で分かっていないのは、これ 1 つだけ。**

Windows + Web、Windows + Android、macOS + Android / iOS は、いずれもできると分かっている。**Windows から iOS だけが未知**で、ここだけが製品の形を変える。

## 問いを間違えないこと

原案は 2 本とも「Windows から iOS を**操作**できるか」を検証項目にしている（初期の企画草案 §15 Phase 0 / 初期の企画草案 §20 Phase 5）。

**問いはこう。**

> **Windows から iOS の画面を、実用的な遅延でリアルタイムに見られるか。**

この製品は、人が AI の操作を横でライブで見ていることが芯（C4）。**操作だけできても、本人が見られなければ ASSIST が成立しない。**その場合 iOS は AUTO 専用となり、製品として別物になる。

## 決めること（このリポで決めてよい・企画側へ選択肢を投げ返さない）

- 使うツールの組み合わせ（go-ios / WebDriverAgent / libimobiledevice / Appium XCUITest Driver / その他）
- 「実用的な遅延」の判定基準を、**先に数字で決める**（何 ms 以内なら人が待たずに見ていられるか）
- 判定基準を決めるにあたって、Android（scrcpy）の実測値を先に取って基準にしてよい

## 作業内容

1. Android の scrcpy でライブビューの遅延を実測し、**比較の基準線**を作る
2. Windows から iOS 実機に接続し、画面をリアルタイムに取得できる経路を探す
3. 取得できた場合、遅延を実測する（基準線と比較する）
4. iOS 17+ のトンネル要件・ペアリング・開発者モードなど、**運用で毎回必要になる手順**を洗い出す
5. 結果を Go / Conditional / No-Go で書く

## 完了条件

- Android の遅延実測値がある（基準線）
- iOS の遅延実測値がある。**取得できなかった場合は、何をどこまで試して駄目だったかが列挙されている**
- 判定が 3 つのいずれかで書かれている
  - **Go** — Windows のまま iOS Adapter を作れる
  - **Conditional** — 条件付きで見られる（条件が明記されている）
  - **No-Go** — 実用にならない
- **No-Go / Conditional の場合、「操作はできるが見られない」のかどうかが明記されている**（iOS を AUTO 専用として残すかの判断材料になる）
- 毎回の接続手順が README に書かれている（人が実機を繋ぐたびに踏む手順）

## 注意

- **この Issue を省略しない。**「どうせ Windows からは無理だろう」で判定を書かない。**駄目だと分かるまで試すのが作業内容**
- **Conditional が出たら、条件を潰す方向で検討する。**条件が付いた時点で落とさない
- **No-Go でもプロジェクトは変わらない。****Windows 版は iOS なしでそのまま出す**（C13）。macOS 専用にはしない
- ただし **C13 は「iOS を諦めてよい」という意味ではない。**「載せない」は**この Issue の判定結果**であって、着手前の前提ではない
- **macOS 機材を調達する話には繋がらない。**この Issue で決まるのは「Windows 版に iOS が載るかどうか」だけ
- 実機は手元にあるものを使う。無い場合はその旨を Issue に書いて止まる（勝手に調達しない）
- **この Issue が終わるまで、Phase 1 以降の実装を始めてよい。**ただし Adapter 境界（Issue 002）だけは、この結果を待って確定させる
