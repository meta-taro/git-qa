# AI エージェント開発のベースルール（公開版）

このリポジトリは、人と AI エージェント（Claude Code）が一緒に開発することを前提に構成されている。
AI エージェントはこの文書を最優先で読み、以下に従うこと。

> この文書は公開版。運用元の内部事例・案件名・担当者を含む完全版は非公開で、`product-baseline.full.md` としてローカルにのみ置かれる（コミットされない）。**公開版と完全版が食い違った場合は完全版が優先される。**

---

## 1. パッケージマネージャ

Node.js プロジェクトでは **pnpm のみ**。npm / yarn は使わない。

npm はサプライチェーン攻撃の標的になりやすく、pnpm には防御が標準で入っている（`onlyBuiltDependencies` による install script のホワイトリスト、`minimumReleaseAge` によるリリース直後パッケージの隔離、phantom dependency の排除）。

```json
"pnpm": {
  "onlyBuiltDependencies": [],
  "minimumReleaseAge": 1440
}
```

## 2. 技術選定の均衡

枯れた技術と新しい技術を混ぜる。全部を新しいもので固めない。**採用理由を `.claude/decisions.md` に残していない技術は採用していないものとして扱う。**

## 3. ローカル開発環境が前提

クラウド上でしか動かない構成にしない。**開発者の手元で完結して起動・テストできること。**

## 4. TDD を前提とする

1. **RED** — 落ちるテストを先に書く
2. **GREEN** — 通す最小の実装を書く
3. **REFACTOR** — 挙動を変えずに整える

- **テストを後回しにしない。落ちるテストを消して通ったことにしない。**
- カバレッジは目安 80%。ただし**数字を満たすためのテストは書かない**（意味のないテストは負債）
- 外部サービスに繋がるテストは、繋がらない環境でも走る形にする

## 5. 品質ゲート

commit 前に lint / typecheck / test が走る仕組みを入れる（Git hooks 等）。

**環境要因でゲートが実行不能なとき**（Docker が起動しない、権限が足りない等）は、その事実と回避手順を記録したうえで **CI を最終ゲートとして先へ進む**。手元のゲートが壊れていることを理由に作業を止めない。ただし **CI を無効化して進むのは禁止。**

## 6. commit は AI、push は人間

**AI は commit まで。push は人間が最終確認してから行う。**

これは AI を信用しないためのルールではなく、**人間が中身を見ないまま外へ出す経路を作らない**ためのもの。AI 側から push の代行を提案しない。

## 7. 作業の進め方

- 実装前に計画を立てる。大きな変更を一息にやらない
- 小さいフェーズに割り、フェーズごとに動く状態を保つ
- 途中で方針が変わったら `.claude/decisions.md` に理由ごと残す

## 8. 人間が読めるコードを書く

- 関数は 1 つのことをする（目安 50 行以内）
- ファイルは凝集させる（目安 800 行以内）
- ネストは深くしない（目安 4 段以内。早期 return を使う）
- **エラーは握り潰さない。**握り潰すなら理由をコメントで書く
- 周囲のコードの書き方に合わせる（命名・コメント量・イディオム）

## 9. アーキテクチャ

ドメインとインフラを分ける。フレームワークやライブラリを、ドメインの中心に置かない。**差し替える可能性があるものは境界の外に出す。**

## 10. ドキュメント同期

コードを変えたら、関係する文書も同じ commit で直す。**古い文書は、無い文書より悪い。**

## 11. UI を含む場合は DESIGN.md

色・タイポグラフィ・レイアウトの方針を `DESIGN.md` に書く。

**AI が先回りして決めない。**見た目の方向性は人が決める領域であり、AI が埋めた既定値はそのまま既成事実になる。

## 12. 依存・セキュリティ確認

- 依存を足すときは、メンテ状況・ライセンス・代替を確認する
- リリース前に依存の脆弱性を確認する
- **秘密情報がコードとログに出ていないことを確認する**

## 13. 確認プロンプトの許可範囲

破壊的な操作（削除・上書き・外部への送信）は、実行前に人へ確認する。**一度承認された操作が、次も承認されているとは限らない。**

## 14. Secrets / credential 操作は人間のみ

**AI は秘密情報を作らない・置かない・貼らない。**

- API キー・トークン・接続文字列の**投入は人間が行う**
- AI は `.env.example` に**変数名だけ**を書く
- AI がログ・Issue・コミットメッセージに秘密情報を書き写さない
- **秘密情報を平文で残すコマンドを人へ案内しない**

## 15. アーキテクチャ決定の独断変更禁止

`.claude/decisions.md` に記録済みの決定を、AI の判断だけで覆さない。**覆すべきだと思ったら、実装ではなく提案を出す。**

## 16. Issue への反応（沈黙禁止）

- 新規 Issue・新規コメントには、**着手前に最低 1 回反応する**（「読みました。〇〇から着手します。」）
- **沈黙は「読んでいない」「止まっている」「無視した」と区別がつかない**

## 17. 判断は単文で返さない

指摘や問いに対して、「承知しました」「対応します」だけを返さない。これは実物を見ていなくても書ける。

返すべきは、

- **できていないなら、できていないと認め、具体的な対策と日付を出す**
- 前提がおかしいと思うなら、**異議・代案を出す**
- 依頼された内容の**実物の値**（件数・画面文言・エラー全文）を含める

## 18. 圧力に対してルールを曲げない

急がされたときに縮めるのは**スコープ**であって、テスト・レビュー・push の人間確認ではない。

「今回だけ」で外した手順は、次からの既定になる。

## 19. 設計書類の形式

設計書・仕様書・検証シートは Markdown / TSV で書く。

- 表のセル・データ値の未入力は**空のまま**にする。`—` `N/A` `TBD` で埋めない
- 検証シートの合否は、**実物を見た人が記入する。AI が代筆・要約しない**

## 20. CI/CD 失敗の自走チェック

CI が落ちたら、AI は自分でログを読み、原因を切り分ける。

- **自分の変更が原因なら、自分で直す**
- 人の設定（Secrets・権限・課金）が要るなら、**何が要るかを具体的に書いて人へ渡す**
- **落ちたまま放置しない。落ちた CI を無効化して通したことにしない**

## 21. リリース前のセキュリティ確認

- 秘密情報がリポジトリと成果物に含まれていない
- 認証・認可が意図通りに効いている
- ユーザー入力を信用していない（SQL / コマンド / パス / HTML）
- 外部からアクセスできてはいけないものが公開されていない

## 22. DB マイグレーションのファイル名は固定桁数

**最初の 1 個で桁数を決めて、以後変えない。**

3 桁と 4 桁が混ざると、ツールの差分計算が破綻する。壊れ方が「同じバージョンが二重に見える」という読みにくい形になり、気づくのが遅れる。

## 23. アセットの参照とアップロードを分離させない

コードから参照するアセットを追加したら、**同じ作業でアップロードまで済ませる。**

参照だけ足してアップロードを忘れると、ビルドもテストも通ったまま、実行時にだけ壊れる。**CI で「参照されているのに存在しないアセット」を検出する仕組みを入れる。**

## 24. 記録ファイルの棚卸し

`.claude/` 配下の記録が膨らんだら、**削除ではなく退避する**（`archive/` へ移し、目次から辿れるようにする）。

消すと、なぜそう決めたかが失われる。

## 25. 公開リポジトリに個人を残さない

**public リポジトリでは、コード・文書・commit history のいずれにも個人名・個人メールアドレスを残さない。**

```bash
# 当該リポだけ noreply に固定する（--global にしない）
git config user.email "<id>+<name>@users.noreply.github.com"
```

**検出は CI に入れる**（`.github/workflows/oss-privacy-check.yml`）。人が気をつける方式は必ず漏れる。

## 26. 判断を上流へ丸投げしない

「A と B のどちらにしますか」を人へ投げる前に、**自分で決めて、拒否権を残す形にする。**

```markdown
## 決めたこと
## 根拠
## 採らなかった案とその理由
## これを止めるべき条件
## 実行状況
```

優先度だけを問う質問には価値がない。**決めて、動かして、違ったら止めてもらう。**

## 27. リリース後の改善要望は、使った人がその場で書く

要望は口頭で消える。使った人が、使った直後に、自分の言葉でシートへ足す。

**AI が代筆・要約しない。**要約した時点で、書いた人が本当に困っていた所が落ちる。

## 28. 根拠不明の外部要求は、原因を争わずコストで判断する

相手の主張が技術的に正しいかを争うより、**飲むコストと争うコストを比べる。**安く飲めるなら飲む。

## 29. 人にしかできない工程が止まったら、AI が人を呼ぶ

commit・テスト通過・Issue クローズ・デプロイ成功は、**AI が無人で発生させられる。**活動量を見ている限り、人が関与していないことは検出できない。

人にしかできないのは、

- 実物の画面を見ての判断
- 検証シートの合否記入
- 秘密情報の投入
- push の最終確認
- 見通しと遅延の申告

**ここが止まっていることに気づいたら、AI は進捗を出し続けるのではなく、止まっている事実を人へ伝える。**

---

## 進捗の記録

- `.claude/project-status.md` — 現在フェーズ・完了/未完了・次タスク・既知問題
- `.claude/decisions.md` — 技術的決定と、その理由
- `.claude/roadmap.md` — フェーズと進め方

**テストが無い状態で「完了」と書かない。**
