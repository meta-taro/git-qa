## 原案のフェーズを組み替える理由

原案 2 本はフェーズの順序が食い違っている。

| | mobile-qa-runner | git-qa-expanded |
|---|---|---|
| Phase 1 | Windows + **Android** | Windows + **Web** |
| Windows→iOS スパイク | Phase 0（最初） | Phase 5（後） |

**どちらも「作りやすい順」で並んでいる。**Android は ADB / scrcpy が成熟している、Web は Playwright で成立しやすい、iOS は Windows から難しいので後ろ。**技術的な難易度で順番が決まっていて、誰がいま困っているかが入っていない。**

痛いのは iOS（2026-08-14 決定）。そして未知も iOS だけ。

**そこで、「測る順」と「作る順」を分ける。**

- **測る順** — iOS が先。ここだけが製品の形を変えるので、早く分岐が判ればよい
- **作る順** — Android が先。既にできると分かっているので、ここで製品の形を固める

Web とデスクトップアプリは、Adapter が効いていれば**足すだけ**（C12）。

## Phase 0: 唯一の未知を測る（実装しない）

**Windows から iOS の画面を、実用的な遅延でリアルタイムに見られるか。**（Issue 001）

操作の PoC より先。**操作だけできても、本人が見られなければ ASSIST が成立しない。**

あわせて、ここでしか決められないものを潰す。

- Adapter の境界を定義する（Issue 002）— 「ライブ映像を出せるか」が線引き
- 既存 OSS の実地調査と「**作らない**」判定（Issue 010）

**完了条件**: Issue 001 の判定（Go / Conditional / No-Go）が**実測に基づいて**出ている。**「試していないので分からない」は完了ではない。**

**No-Go でもロードマップは変わらない**（C13）。**Windows 版は iOS なしでそのまま出す。**決まるのは「Windows 版に iOS が載るかどうか」だけ。

**ただし C13 を「iOS を諦めてよい」と読まないこと。**まず挑戦するのがこの Phase の中身で、「載せない」は**判定の結果**。Conditional が出たら条件を潰す方向で検討する。

**なぜ最初か**: 早く分かれば Adapter 境界（Issue 002）を一度で決められる。**後で分かると、境界を引き直すことになる。**

## Phase 1: Android で一本道を通す 🎯最初の山

> **実在のテストケース TSV を読み込み、Android 実機を AI が操作し、人が横でライブで見て、1 打鍵で `VERIFIED` を置き、`run.json` が出るまで。**

通す流れ:

```
TSV を読む（書き戻さない）
 → Android 実機に接続
 → scrcpy のライブビューが画面中央に出る
 → AI がケースを実行する（人は横で見ている）
 → AI が「判断保留」と言う / 落ちる / 差分が出る
 → 人が 1 打鍵で VERIFIED を置く
 → 次のケースへ自動で進む
 → runs/<ts>/<caseId>/ に証跡が出る
```

**完了条件**: 5 ケース以上をこの流れで通し、`run.json` に `VERIFIED` と `AUTO_PASS` が混在した状態で出る。ライブビューの遅延が実測で許容範囲に入っている（Issue 005）。

この時点で無くてよいもの: iOS / Web / デスクトップ / MCP / 録画 / Git 連携 / Finding / AUTO モード。

**なぜここを最初にするか**: この一本が通れば、製品が解こうとしている問題（**人が楽をしながら自分で保証する**）が実物で見える。逆に、これが通るまでは何も見せられない。

---

## Phase 2: 楽になったことを数字で示す

Phase 1 は「動く」。ここで**「楽になった」を測る**（C7・Issue 008）。

- 同じ 20 ケースを、手で通した時間と、この道具で通した時間
- 手数の実測（1 ケースあたりの打鍵数・マウス操作回数）

**完了条件**: 手作業比の所要時間が明確に短い。**短くなければ、Phase 3 へ進む前に UI を作り直す。**

**ここが製品の生死を決める。**他が全部できていても、この数字が出なければ MVP ではない。

---

## Phase 3: 証跡を残す

- スクリーンショット / 動画 / ログ を `runs/<ts>/<caseId>/` へ
- **録画は開始時の設定。モードに紐づけない**（C11）
- **`run.json` に「録画しなかった」を残す**（C11）
- Git commit。**動画は既定で Git に入れない**（C29 / Issue 007 の試算）。`runs/` はローカル保管が既定で、Git LFS はオプトイン

**完了条件**: 録画あり / 録画なしの両方で走らせ、`run.json` からその区別がつく。

---

## Phase 4: MCP / AI 協調

- `test.*` / `device.*` / `human.*` / `git.*` を MCP Server として出す
- **`test.complete` は TSV を書かない**（C3）。`run.json` に出すだけ
- Human Takeover（Take Control / Return to AI / Pause / Retry Step / Skip Step / Abort Case）
- Finding（テスト中に見つけた別の問題を、ケースの合否とは別に記録する）

**完了条件**: エージェントが git-qa と md-business の両方を呼び、実行結果が md-business 経由で TSV に反映される。

---

## Phase 5: ついでの Adapter

Adapter が効いているかの答え合わせを兼ねる。

- **Web Adapter**（Playwright headed。ミラーリング不要）
- **デスクトップアプリ Adapter**

**完了条件**: Adapter を足すのに、コア側の変更が要らなかったこと。**要ったなら Phase 0 の境界定義が間違っている。**

---

## Phase 6: iOS（Issue 001 の結果で分岐）

- **成立していた場合** — Windows のまま iOS Adapter を足す
- **条件付きだった場合** — 条件を潰せるか検討してから決める。**条件が付いた時点で落とさない**
- **不成立だった場合** — **Windows 版に iOS は載せない。**そのまま出す（C13）

### 不成立時に macOS 版を作る話にはならない（重要）

不成立だったときの逃げ道は、**「その検証は mac で人がやる」という運用の話**（2026-08-14 決定）。**製品に macOS 版を足す話ではない。**

- ❌ 「Windows で駄目だったので macOS Adapter を MVP に入れる」
- ✅ 「Windows 版に iOS は載らない。iOS の検証が要る人は mac でやる」

**この 2 つを混ぜると、MVP が macOS 対応を抱え込んで肥る。**macOS 対応は将来の別枠で、**MVP には入れない。**

**完了条件**: 載せる場合、iOS 実機で Phase 1 と同じ一本道が通る。載せない場合、**その旨が README に書かれている**（利用者が期待して落とさないように）。

## フェーズ境界の判断基準

迷ったときの優先順位。

1. **本人の手間が減ること**（これを落とすと使われない道具になる）
2. ライブで見られること（遅延・手数）
3. 証跡が後から読めること
4. 対象の広さ
5. それ以外
