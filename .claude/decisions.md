# git-qa — 決定事項（叩き）

- 作成: 2026-08-14
- 出典: 原案 2 本 + 2026-08-14 のプロダクトオーナーとのやり取り

---

## 確定済み

### C1: 結果の語彙は `VERIFIED` / `AUTO_PASS` を分ける

`VERIFIED` = 人が名前を置いた。`AUTO_PASS` = AI が通しただけで誰も見ていない。

**Why**: 原案 `mobile-qa-runner` の素の `PASS` だと 2 つが同じ値に潰れる。この製品の存在理由は「人が保証したこと」を残すことなので、潰した時点で意味がなくなる。`git-qa-expanded` 側の語彙が正しい。

---

### C2: 不正防止機構を作らない（非目標に明記する）

中身を見ずに `VERIFIED` を置くことはできてよい。

**Why**: 証跡は偽装を防ぐためのものではない。**置いた瞬間にその人の名前が残る＝ロックではなく署名。**丸投げして事故が起きたときに困るのは置いた本人なので、道具側で防ぐ必要がない。明記しないと実装者が善意で承認フローを作り始め、**楽をするための道具が重くなる。**

---

### C3: TSV へ書き戻さない

git-qa は TSV を読むだけ。結果は `run.json` に出す。TSV への反映は md-business が行う。

**Why**: (1) TSV の書式規約（行 ID・`computed`・`hidden`）を git-qa が抱えずに済み、md-business の仕様変更に追随不要になる。(2) md-business を持たない利用者が自前で書くと、集計列を実数で潰す・控えの行を復活させるといった壊し方をする。**読める形のまま壊れるので気づけない。**

同一のエージェントが git-qa と md-business の両方を操作するので、橋渡しはエージェント側で成立する（2026-08-14 決定）。

---

### C4: 実行中の主媒体はライブビュー。動画は保管物

UI の中心は録画プレイヤーではなくミラーリング。Android は scrcpy を前提とする。Appium のスクリーンショット連写は使わない。

**Why**: 人は AI が操作しているのをその場で見ている。動画は「あとでどうだったっけ」と第三者提出のためのもの。**遅延が 1〜2 秒あると「固まったのか遅いだけか」が分からず、人が手を出す。**その時点で道具の目的が達成されない。

---

### C5: 人が見るのは「AI 判断保留」「差分」「失敗」の 3 つだけ

全ケースの人間確認を強制しない。

**Why**: ノルマ化すると使われなくなる。ASSIST の本体は「AI が全部やる」ではなく「AI が見る場所を絞る」。

---

### C6: `VERIFIED` は 1 打鍵で置け、置いたら次ケースへ自動で進む

**Why**: 判断が正しくても、そこに至る手数が多ければ楽になっていない。動画をシークしてボタンを探す導線を作った時点で手作業より遅くなる。

---

### C7: 主指標は「同じケース群の所要時間（手作業比）」

同じ 20 ケースを手で通した時間と、この道具で通した時間を測る。後者が明確に短いこと。

**Why**: 原案 `git-qa-expanded` §22 の「従来の手動チェックより明確に楽」は主観のままで判定できない。**この数字が出ないなら、他が全部できていても MVP ではない。**

---

### C8: Adapter に入るかは「ライブ映像を出せるか」で決まる

Web / Android / デスクトップアプリは入る。API / CLI / バッチは入らない（別の見せ方が要る）。iOS は D1 の結果次第。

**Why**: ライブビューが芯（C4）である以上、映像が出せない対象では ASSIST が成立しない。原案 `git-qa-expanded` §21 は Phase 8 で API / CLI を同じ枠に足そうとしているが、**同じ Adapter には入らない。**

---

### C9: 測るのは iOS が先。作るのは Android が先

Phase 0 で Windows→iOS のライブビュー可否だけを測る。実装の MVP は Windows + Android から。

**Why**: 未知は Windows→iOS だけで、そこだけが製品の形を変える。Android は既にできると分かっており、macOS なら Android も iOS もできる算段がある＝**最悪ケースでも製品は死なない。**原案 `mobile-qa-runner` §4 は同じ事実を「だから全体の成立条件にしない」＝後回しの根拠に使っているが、**死なないからこそ先に試せる。**分岐が早く判れば設計を戻さずに済む。

---

### C10: OSS 公開物に実証跡を混ぜない

サンプル・ドキュメントはダミー案件で作る。OSS にする場合は commit history に個人名・個人メールも残さない。

**Why**: 証跡には実画面が写る。顧客へ返すもの自体は問題ないが、公開リポに混ざると回収できない。

---

### C11: 録画の on/off は実行開始時の設定。モードに紐づけない

**Why**: どのモードで録画が要るかは、その時の人が決めること（2026-08-14 決定）。道具側で「AUTO なら録画」と決め打つのは越権。

付随して必須になるもの: **`run.json` に「録画しなかった」を残す。**動画が無いときに「オフで走らせた」のか「録画に失敗した」のかを区別できないと、後から証跡として読めない。

---

### C12: Web はデスクトップアプリと同じく「ついで」で足す

Adapter が効いていれば追加コストが小さい。ただし**最初の正式対象にはしない。**

**Why**: 原案 `git-qa-expanded` §5 は「WebはWindows版MVPの最初の正式対象とする」と書いているが、これは**作りやすい順**であって痛い順ではない。順序は C9 に従う。

---

### C13: 挑戦して駄目だった場合、Windows 版は iOS なしで出す。macOS を MVP の前提にしない

**まず挑戦する（Issue 001）。**そのうえで Windows→iOS が不成立だった場合に、**Windows 版は iOS を含まない形でそのまま出す。**macOS 専用にはしない（2026-08-14 決定）。

**これは「iOS を諦める」決定ではない。**（2026-08-14 確認）

| 誤読 | 正しい読み |
|---|---|
| iOS はスコープ外なので Issue 001 は省略してよい | **Issue 001 は必ず実施する。**省略は No-Go ではない |
| 難しそうなので早めに切り上げてよい | **駄目だと分かるまで試す。**判定を出すことが完了条件 |
| iOS が載らない前提で設計してよい | 載る前提で Adapter 境界を引く（Issue 002）。載らないと分かったときに外す |

**「載せない」は判定の結果であって、着手前の前提ではない。**Conditional（条件付きで見られる）が出た場合は、**条件を潰す方向で検討する。**そこで即座に落とさない。

**Why**: mac を前提にすると、**Windows で動く道具という前提そのものが崩れる。**初期の企画草案 §4 が「macOS Adapter があるから全体の成立条件にしない」と書いたのは正しいが、その先を「不成立なら macOS へ乗り換える」と読むと本末転倒になる。**乗り換えるのではなく、載せないだけ。**

帰結:

- **Issue 001 の優先度は下がらない。**最初に着手する（Phase 0）
- **結果でロードマップも設計も揺れない。**決まるのは「Windows 版に iOS が載るかどうか」だけ
- 不成立でも Web / Android / デスクトップアプリで製品としては成立する（C8）
- macOS 対応は将来の別枠。**MVP には入れない**
- **機材の判断には繋がらない**（No-Go が出ても mac を買う話にはならない）

---

### C14: 製品名・リポ名は `git-qa`

初期の企画草案 §27 の第一候補を採る（2026-08-14 決定）。`qa-runner` / `qa-evidence` は不採用。

**Why**: 対象が Web / デスクトップまで広がるので、mobile を含む名前は使えない。`git-qa` は「証跡が Git に残る」という一番外しにくい特徴を名前にしている。

---

### C15: OSS として公開する（2026-08-15 確定）

`meta-taro` 配下の OSS 系列（`dbboard` / `md-business`）に並べる。**D2 は解決。**

**Why**: 公開して差し支えのある要素が無く、掃除のコストも公開直前の squash 1 回で足りる。決めた以上、**最初から公開前提の作法で作れる**（後から倒すより安い）。

**この決定で必須になるもの**:

- **個人名・個人メールの検出 CI を最初から入れる**（Issue 003�）
- **サンプル・テストデータはダミー案件で作る**（C10）
- **証跡リポを本体と分ける**（C16）
- README・ドキュメントに**顧客名・対象サイト名・案件名を書かない**

---

### C16: 本体（公開）と証跡（非公開）を必ず別リポにする

C15 の帰結。**同じリポに入れてはいけない。**

| | history | 公開 |
|---|---|---|
| **本体** `meta-taro/git-qa` | 要らない。公開直前に squash してよい | **する** |
| **証跡**（実運用） | **history が中身。**消せない | **しない** |

**Why**: 「証跡が Git に残り、第三者が後から遡れる」がこの製品の機能そのもの（名前の由来・C14）。証跡リポの history を消すと売りが消える。**一方で本体は history を消せる。消せる側と消せない側を混ぜると、消せない側に消したいものが入る。**

**未定**: 証跡リポの名前・置き場所（顧客ごとに作るか 1 本か）。**本体の作業は止まらない。**

### C17: `VERIFIED` を AI の型に入れない（2026-08-17）

C1 の実装。結果の語彙を 1 つの型で持たず、**誰が置いたかで型ごと分ける。**

| 定数 | 中身 | 置く人 |
|---|---|---|
| `AI_RESULTS` | `PASS` / `FAIL` / `BLOCKED` / `SKIP` | AI |
| `HUMAN_RESULTS` | `VERIFIED` / `FAIL` / `BLOCKED` / `SKIP` | 人 |
| `CASE_RESULTS` | 上記の合併（`AUTO_PASS` を含む 5 値） | 出力される値 |

`AUTO_PASS` はどちらの入力にも無い。**`resolveCaseResult` が「AI が `PASS` と言い、人が何も置いていない」場合にだけ作る値**であって、誰かが直接置ける値ではない。

**Why**: C1 を enum 1 本で表すと、AI 側の実装が `VERIFIED` を代入できてしまう。禁止をレビューで守らせる形にすると、いずれ通る。**型として持たせなければ、書こうとした時点でコンパイルが落ちる。**

---

### C18: `run.json` の正本は JSON Schema ファイル。TypeScript の型は写し（2026-08-17）

`packages/core/schema/run.schema.json`（draft 2020-12・`$id: urn:git-qa:schema:run:v1`）が正本。検証は ajv で行う。TS の型は編集の助けであって、検証はしない。

**両者がずれていないことをテストで見る**（TS の定数配列と Schema の `enum` を突き合わせる）。

**Why**: `run.json` は git-qa の**外**へ出る（証跡リポ・md-business・第三者のレビュー）。読む側は TypeScript を持っているとは限らない。**外に出る形の正本を、こちらの言語の型にしない。**`$id` を GitHub URL にしないのは、公開先のオーナー名を実装が先回りして決めないため（C15 の置き場は決まっているが、URL を焼くと移せなくなる）。

---

### C19: 「どの機体・どのビルドで走らせたか」は TSV でなく `run.json` に持つ（2026-08-17）

検証シートに `対象機種` のような列を足さない。`run.json` の `target`（`kind` / `device` / `build`）に持つ。

**Why**: 同じシートを Pixel と iPhone と別ビルドで**何度も**走らせる。シートに書くと 1 枚が 1 機体に縛られ、機体の数だけシートが増える。**シートは「何を確かめるか」、run は「いつ・どれで確かめたか」。**C3（TSV へ書き戻さない）とも整合する — 列を足せば、いずれ埋めたくなる。

---

### C20: 録画は 4 状態で持つ。「録画していない」と「録画に失敗した」を同じ値にしない（2026-08-17）

`recording.state` は `recorded` / `not_requested` / `failed` / `unsupported`。`failed` と `unsupported` は `reason` が必須、`not_requested` には `reason` を書けない。

**Why**: C11 で録画は実行開始時の設定になった。**動画が無いときに「オフだった」のか「録れなかった」のかが分からないと、証跡として提出したときに説明できない。**「ファイルが無い」で表すと必ず潰れるので、状態を明示的に持つ。

---

### C21: 検証シート TSV は CRLF のまま保つ（2026-08-17）

`.gitattributes` で `*.tsv -text`。git の改行正規化から外す。

**Why**: md-business の `test-spec-tsv/v1` は CRLF が仕様のうち。正規化されると「パーサは通るが元ファイルと 1 バイト違う」状態になり、C3（読むだけで書き換えない）を確かめるハッシュ比較が意味を失う。

---

### C22: 自動整形はコードだけにかける。Markdown と TSV にはかけない（2026-08-17）

`.prettierignore` に `*.md` と `*.tsv`。

**Why**: `.claude/rules/product-baseline.md` と `.claude/templates/` は上流から配布される。整形をかけると、次の配布のたびに中身と無関係な差分が出て、本当の変更が読めなくなる。TSV は列区切りが仕様なので、整形すれば単に壊れる。

---

### C23: install script は `esbuild` だけ通す（2026-08-17）

`pnpm-workspace.yaml` の `allowBuilds` に `esbuild` のみ。他は既定どおり全て止める。

**Why**: vitest → vite が依存し、postinstall がプラットフォーム別バイナリを配置する。**開発時にしか使わず、成果物には入らない。**通す理由をここに書けないものは通さない。

### C24: Adapter は「ライブ映像を出せる」ことを型で必須にし、画面の状態は生データのまま渡す（2026-08-17）

`TargetSession.liveView` は省略できない。`Observation.raw` は `unknown` で、コアは解釈しない。詳細と Web を当てた結果は `docs/adr/0001-adapter-boundary.md`。

**Why**: C8 の線引き（ライブ映像を出せるものだけが Adapter に入る）を文書に書くだけでは守られない。任意にすれば、映像を出せない対象は「実装しなければいい」だけで入ってくる。**入れられない形にする**のが唯一効く（C17 と同じやり方）。状態のほうは逆で、DOM とアクセシビリティツリーは同じものの方言ではないので、共通の型へ潰すと潰した時点で情報が落ちる。

### C25: テスト用の Fake アダプタを `packages/core` に同梱して輸出する（2026-08-17）

`createFakeAdapter()` と契約テスト `test/adapter/contract.ts` を core 側に置く。

**Why**: 実機・adb が無くても芯（人が見て保証する流れ）を通しで動かせるようにするため。下流のパッケージが対象なしでテストを書くのにも要る。契約テストを「実装ごとに当てる束」として置いておくと、Android / Web を足すときの答え合わせがそのまま走る。

### C26: 実行器は「繋ぐ前に落とす・途中では落ちない」（2026-08-17）

`executeRun()` の失敗の置き方を 2 つに分けた。

- **繋ぐ前に落とす**: シートの不備（`No.` の重複 / 非整数 / `項目` が空 / 列の欠落）、`mode` と人へ聞く口の食い違い。**繋いでから落ちると、端末を掴んで何もせず離すことになる**
- **途中では落ちない**: ケースの実行が例外を投げても `FAIL` として残し、後続を続ける。録画の停止が失敗しても合否は残し、`{state:'failed', reason}` に理由を書く

**Why**: 途中で throw すると、そこまで走らせた分の証跡ごと消える。**1 件落ちたことより、走った 20 件が残らないことのほうが痛い。**

**併せて決めたこと**

- 録画は**ケースの操作までで閉じる**。人が考えている時間を動画に入れない（後から見返すとき、無音の停止画が延々と続くだけで読めなくなる）
- `recording.requested` と `target` は**セッションから取る**。呼び出し側に二重に書かせない（食い違ったときにどちらが正か決まらない）
- `run.json` は**スキーマを通らなければ書かない**・**同じ `runId` に 2 度書かない**。壊れた証跡と、黙って消えた証跡を作らない

---

### C27: ライブ映像はストリームを取り込んで自前で描く。骨格は Tauri（2026-08-17）

**他プロセスの映像を遅延なくウィンドウ内に出せるか**が、この製品の骨格に固有の要件（C4）。骨格を選ぶ前に実測した。

- **方式 A（生 H.264 を受け取り、アプリ内で復号して canvas に描く）**を採る。枠の中に自由に置け、ケース一覧・判定欄と重ねられる
- 骨格は **Tauri**。Windows の WebView2 ＝ Chromium で、下の実測がそのまま当てはまる。Rust 側で scrcpy / adb の受け口を持てる（C24 の実装先として自然）

**実測**（Windows / Chromium・31 秒）: 受け取り 1892 / 描画 1891（取りこぼしなし）・60.3 fps・復号の待ち 2.9 ms・最初の絵まで 648 ms。

**実機は使っていない。**scrcpy が吐く形（生 H.264 Annex-B の 1 本のストリーム）を ffmpeg で作って代役にした。**確かめたのは端末との接続ではなく、映像を GUI の中に出せるかだけ。**

詳細・弱いところ・覆すべき条件は `docs/adr/0002-live-view-embedding.md`。**macOS / Linux は未測定で、そこが駄目なら Tauri の判断は覆る。**

### C28: デスクトップ骨格の作り（2026-09-01）

C27 で決めた Tauri の中身を、`packages/desktop` として置いた。作りで決めたのは 4 点。

- **フロントのビルドは Vite。**`vite` は既に vitest 経由で依存グラフに入っており（`vite@7.3.6`）、明示 devDependency にしても**新規に増えるパッケージが無い**。`^7.3.6` で留める（既定で解決される 8 系を入れると vite が 2 メジャー同居し、上の根拠が崩れる。vitest 3.2 の peer も `^5 || ^6 || ^7`）
- **DOM のテストは happy-dom。**「空の 3 カラムが出る」を実際の DOM で検査する。純粋な関数だけを検査する形にすると、**画面が出ていないのにテストが通る**状態を作れてしまう
- **3 カラムの構成は TypeScript 側（`src/columns.ts`）に一本化する。**幅は CSS へ `--column-flex` として渡し、CSS に数字を書かない。2 箇所に同じ数字を置くと、片方だけ直された状態に気づけない
- **`tsc` は型検査だけに使う**（`emitDeclarationOnly`）。配るものは Vite が `dist/web` へ出す。同じ JS を 2 系統から吐かせない

**中央（ライブビュー）が左右より広いことを、テストで固定した。**C4 / PRD §2 のとおりここが主媒体で、中央が狭くなる変更は見た目の調整ではなく製品の前提を崩す変更なので、テストで落とす。

**色・タイポグラフィは決めていない。**`DESIGN.md` が全項目空で、見た目は人が決める領域（product-baseline §11）。骨格は独自の色を持たず、枠線は `currentColor` から作り、配色は OS の設定に従う。**アイコンも Tauri の既定のまま。**ここを AI が埋めると、そのまま既成事実になる。

**Cargo の `authors` は置かない**（product-baseline §25）。アプリ識別子は `dev.gitqa.desktop`。既定の `com.tauri.dev` は Tauri 側の予約値で、そのままでは配布物を作れない。

### C29: 動画は既定で Git に入れない。録画そのものは既定 on（2026-09-02）

Issue 007 の試算から。**Git LFS の無料枠は、この製品の証跡量に対して小さすぎる。**

**2026-09-02 に Android エミュレータで実測し、数字を差し替えた。**
最初は scrcpy の既定ビットレート 8 Mbps（上限）で置いて「24 GB / 月・約 9 営業日で無料枠が尽きる」と
書いたが、**実測は 11 分の 1 だった。**

実測（scrcpy 4.1・Pixel 3a / API 31 エミュレータ・設定画面をスクロール・実時間 60 秒）:
**5.05 MB / ケース**（1.28 Mbps の映像区間 / 0.71 Mbps の実時間平均）。

**scrcpy は画面が変化したときしかフレームを作らない。**8 Mbps は上限であって実際に出る値ではない。
**容量は実時間ではなく画面が変化した量に比例する**ので、人が考えている時間・AI が待っている時間は
ほぼ容量を食わない。

| | 上限で置いた場合 | **実測ベース** |
|---|---|---|
| 20 ケース × 20 営業日 | 24 GB / 月 | **2.12 GB / 月** |
| 無料枠 10 GiB（Free / Pro）まで | 約 9 営業日 | **累積で 5.1 か月** |
| Team / EC 250 GiB まで | 11.2 か月 | **累積で 127 か月** |

**それでも決定は変わらない。**

- **ストレージは Git の履歴に入る以上、青天井に累積する。**月 2.12 GB でも無料枠は 5 か月で尽きる。
  **どんなに小さい月次でも、固定枠はいつか超える**
- **帯域のほうが先に破裂する。**5 か月ぶん（10.7 GB）を溜めたリポを**1 回 clone しただけで
  月間帯域 10 GiB を超える。**開発者が 1 人増えるたびに起きる
- **ただし Team / Enterprise Cloud（250 GiB）なら 10 年以上もつ。**そちらでは LFS は現実的な選択肢で、
  「LFS は無理」ではなく「無料枠では無理」が正しい

**決めたこと**

1. **動画は既定で Git に入れない。**`runs/` を `.gitignore` に入れ、ローカル保管を既定にする
2. **録画そのものの既定は on。**保管が Git の外なら、費用は課金ではなくディスク。**off にする口は必ず出す**（C11）
3. **古い Run を自動で消さない。**消すのは人の判断（消すと、なぜそう判定したかの根拠が消える）
4. **Git LFS はオプトイン。**使う場合の試算と「単価は料金計算機で確認すること」を文書に書く

**Why**: 費用は自社なら案件原価として説明が付くが、**OSS の利用者にはそのまま降りる**（Issue 007）。
既定で課金経路に乗せる設計にしない。**既定を「入れない」にしたので、超過単価が分からなくても
既定の月額は 0 で確定する。**

**費用を理由にライブビューや証跡そのものは削っていない。**削ったのは動画の保管先だけ
（Issue 007 の注意書き）。`run.json` とケースの合否は従来どおり残る。

**この決定の弱いところ**

- **実測はエミュレータであって実機ではない。**GPU は swiftshader、内容は設定画面のスクロールだけ、
  端末は 1 台（API 31）。**写真・動画・アニメーションの多い実アプリはもっと出る。**
  真の値は上限 8 Mbps と実測 0.71 Mbps の間のどこかで、**実機での測り直しが要る**
- **超過単価が一次情報から取れていない。**docs.github.com に記載が無く、料金計算機へ誘導される。
  加えて `github.com/pricing` は docs 側が「廃止した」と書くデータパックを今も表示しており、
  **一次情報どうしが食い違っている**

**これを覆すべき条件**

- 実機の scrcpy で録った実測が、**Free / Pro の無料枠に累積でも収まる**と分かった（エミュレータの実測では 5.1 か月で尽きる）
- 利用者から「証跡が Git に無いと運用にならない」という要求が実際に出た（そのときは LFS ではなく
  別ストレージを含めて置き方を選び直す）

### C32: 端末の生 H.264 は `adb exec-out screenrecord` から取る（2026-09-02・暫定）

D6 の決着。**scrcpy のサーバへ直接繋ぐ（A）のではなく、Android 標準の `screenrecord` に
生 H.264 を吐かせる（B）。**

**Why**: PRD §2 の「scrcpy 前提」と §11 の非目標「scrcpy の再実装」が正面から当たっていた。
**先に安いほう（B）を実装して測り、足りなければ A へ進む**という順にした。実装は数十行で、
端末へ何も送り込まない。

**実測（Pixel 3a / API 31 のエミュレータ・操作を流しながら）**

| | 値 |
|---|---|
| 受け取り | 1,216,253 バイト / 32 枚 / 4,793 ms |
| 最初の 1 枚まで | **491 ms** |
| 実効ビットレート | 約 2.0 Mbps |

`adb` → 生 Annex-B → `createAnnexBSplitter` → IDR を含む枚、まで通った。

**`--output-format=h264` は `screenrecord --help` に載っていない**（AOSP の隠しオプション）。
実際に叩いて確認している。

**暫定である。A へ戻る条件を残す**（詳細は `docs/adr/0003-live-view-transport.md`）。

- Issue 005 で測った**操作から表示までの遅延**が上限を超えたとき
- `--output-format=h264` が通らない端末が出たとき（隠しオプションなので保証が無い）
- 180 秒ごとの繋ぎ直しが、実運用で目に見える切れ目になったとき

**併せて決めたこと**

- **`LiveViewTransport` に `h264-stream` を足した**（この型は「対象を足すときに増やす」設計）。
  **映像を読む口（`frames()`）は `h264-stream` のときだけ生やす。**別窓の実装に空の口を
  持たせると、**映像が来ないのか、そもそも通らない方式なのかが区別できなくなる**
- **どちらの方式を使うかは呼ぶ側が選ぶ。**既定は従来どおり別窓。遅延を測ってから既定を変える
- **生 H.264 の切り出し（`createAnnexBSplitter`）はコアへ移した。**UI 固有ではなく、
  映像を出す側（アダプタの検査）も描く側（デスクトップ）も同じ切り方を使う

**この決定の弱いところ**

- **測ったのは「繋いでから絵が出るまで」であって、「操作してから画面に出るまで」ではない。**
  人が待つかどうかを決めるのは後者（Issue 005）
- **エミュレータであって実機ではない**
- **180 秒の上限を跨ぐ繋ぎ直しを実装していない**
- **`webcodecs.ts` の codec 文字列が固定**（`avc1.42E01E`）。端末が吐いた SPS は Level 5.0 で
  食い違っている。**本来は SPS から組み立てるべき**

### C33: Node 側と画面側は localhost の HTTP で繋ぐ（2026-09-02）

`packages/live-bridge`。アダプタ（Node で動く）が流す生 H.264 を、画面（webview で動く）へ渡す。

**Why HTTP**: スパイクで実測した経路をそのまま使える（ADR 0002）。**Rust を書かずに済み**、
`fetch` のストリームで読めるので受け手側に依存が要らない。

**守りを 2 つ入れた。**ここを流れるのは**検証中の端末の画面**で、顧客名や電話番号が写る（PRD §10）。

1. **127.0.0.1 でだけ待ち受ける。**外から届く口にしない
2. **URL に無作為の 32 文字を入れる。**同じ PC の別プロセスから当てずっぽうで覗けないように。
   **localhost なら安全、ではない**

**実測（Pixel 3a / API 31 のエミュレータ）**

| `screenrecord` 直結 | 1,158,406 バイト / 32 枚 / 最初の 1 枚まで 370 ms |
| 端末 → アダプタ → 橋 → 受け手 | 777,238 バイト / 20 枚 / 最初の 1 枚まで 641 ms |

**併せて直した 3 つ**

- **`@git-qa/core` の入口が Node 専用のファイル IO を巻き込んでいた。**webview 側から使うと
  バンドルできない（`node:fs` が解決できず**実際にビルドが落ちた**）。
  **ブラウザでも読める入口 `@git-qa/core/live` を分けた**
- **`pnpm verify` に `build` が入っていなかった。**上のビルド失敗を、テストが全部通ったまま
  取り逃がしていた。**`verify` の最後に `build` を足した**（CI もこれを走らせる）
- **実機に当てる検査は 1 台の端末を取り合う。**ファイルを並行させると、片方の操作が
  もう片方の `uiautomator dump` を壊す（**実際に落ちた**）。`GIT_QA_ANDROID_E2E=1` のときだけ
  ファイルの並行を止める

**この決定の弱いところ**

- ~~橋を起こして URL を画面へ渡す「宿主」がまだ無い~~ → `packages/host` で解消（2026-09-02）。
  **ただし webview が橋に繋いで描く所は未確認**（画面のロック）
- **測ったのは「繋いでから絵が出るまで」で、操作から表示までではない**（Issue 005）
- **無作為の文字列は覗き見を防ぐだけで、暗号化はしていない。**同じ PC の中を流れる前提

### C34: AI が `PASS` / `FAIL` を出せる条件を、機械で見られる場合だけに絞る（2026-09-02）

`packages/core/src/run/steps.ts` / `case-runner.ts`。Issue 004 の「**AI が判断保留を出す条件**」。

**AI が自分で結果を決めてよいのは、期待結果が「」で囲まれた文字列 1 つで、それが画面の文字に
在るか無いかで決まるときだけ。**それ以外は全部 `BLOCKED`（判断保留）にして人へ渡す。

| 状況 | AI の結果 |
|---|---|
| 期待結果が `「X」と表示される` で、画面に `X` が在る | `PASS` |
| 同上で、画面に `X` が無い | `FAIL` |
| 期待結果に鉤括弧が 0 個（例: `ホーム画面が表示される`） | **`BLOCKED`** |
| 期待結果に鉤括弧が 2 個以上（どれを見るか決められない） | **`BLOCKED`** |
| 手順を操作へ落とせない（例: `メモを長押しする`） | **`BLOCKED`**（**端末に触らない**） |
| 非 ASCII の入力（端末の `input text` は IME を通らない） | **`BLOCKED`** |
| 操作の途中で落ちた・画面の文字が読めない | **`BLOCKED`** |

**Why 控えめに倒すか**: AI が推測で `PASS` を積むと、**人が見ていない `AUTO_PASS` が増えるだけ**で、
この製品の意味（誰が保証したかが証跡に残る・C1 / C17）が薄れる。**通ったことにするより、
判断を人へ渡すほうが安い。**

**推測しない。**「何も入力せずに保存をタップする」は、`保存` を取り出す推測をせず、
`何も入力せずに保存` という要素を探しに行って**見つからず `BLOCKED`** になる。
文を読み解いて別の要素を触ると、画面は動くので通ったように見え、**間違いに気づけない**
（`adapter-android` で要素の指定を完全一致だけにしたのと同じ理由・C31）。

**判定したことしか書かない。**`PASS` の注記は「画面の文字に「X」が在ることだけを見た」。
`「あいうえお」のメモだけが一覧に残る` のような**排他は確かめていない**ので、主張しない。

**この決定の弱いところ**

- **手順の語彙が 2 つしかない**（タップ / 入力）。スワイプ・長押し・キー入力は全部 `BLOCKED` になる。
  **足すのは、実際のシートで詰まってからにする**
- **画面の文字をどう取るかはアダプタ側**（`readScreenText`）。コアは形を知らない（C8）
- **この規則で実シートを流したのはまだテストの中だけ。**実機で 5 ケース通していない

### C37: 打鍵と実行状態は、映像と同じ橋で往復させる（2026-09-02）

### C39: 既存 OSS を採らずに作る。**自作するのは「結果の語彙」だけ**（2026-09-03）

Issue 010 の判定。**「独自性があるから作る」ではない。**

**どの製品も、人が見た PASS と誰も見ていない PASS を同じ値にする。**

| 製品 | 結果の語彙 |
|---|---|
| Playwright | `passed / failed / timedout / interrupted` |
| Maestro | `SUCCESS / ERROR` |
| Allure Report OSS | `status` ＋ 自由な `labels` |
| ReportPortal | `PASSED / FAILED / SKIPPED / INTERRUPTED / …` |
| Allure TestOps（商用） | `Passed / Failed / Skipped / Broken / Unknown` |

**ReportPortal だけが、この軸を部分的に持っていた。**`IssueEntity.auto_analyzed`（真偽値）で
「自動解析が付けた分類か、人が付けたか」を区別している。**この軸が実務で要ることの裏付け。**
ただし持っているのは**失敗の分類だけ**で、**成功側には無い**。

**自作しないもの**（既存に寄せる）

- 端末の操作と画面の取得 — `adb`（将来は scrcpy のサーバも候補）
- 見ながら触る体験 — scrcpy が示した形をそのまま採る
- 証跡の見せ方 — Allure / ReportPortal へ寄せられる可能性がある。**いま作らない**

**「既存へ貢献する」を採らなかった理由**: ReportPortal に「人が見た PASS」を足すのは、
**結果の語彙そのものを変える提案**になる。外部製品の中核データ構造を変える提案は通る見込みが薄く、
通っても見通しが立たない。**こちらの語彙を持ったまま、出力側で寄せるほうが現実的。**

**この決定を覆すべき条件**

- どこかの製品が「人が見た」を**結果の値**として持ったら、こちらの語彙を捨てて寄せる
- **主指標（手作業との所要時間比較・C7）で手作業に負けたら。**速くならないなら、
  語彙が正しくても作る理由が無い

### D2: OSS として公開するか → **C15 で解決（2026-08-15）**

以下は判断に使った材料。**公開して差し支えのある要素は無い。**

ただし**掃除ができるのは今だけ**という制約がある。

- **commit history は後から消せない。**個人名・個人メールが入ると、公開時に history ごと作り直すことになる
- **サンプル・テストデータに実案件のものを使うと、後から差し替えても history に残る。**証跡には実顧客の画面が写るので、ここが一番危ない

**推奨**: **いま OSS と決める。**決めれば最初から公開前提の作法（検出 CI・ダミー案件でのサンプル）で作れる。`dbboard` / `md-business` と同じ `meta-taro` 配下の OSS 系列に並ぶ。

### history は公開直前に 1 回消せばよい（2026-08-14 決定）

「最新が動いていれば history は要らない」＝**公開時に squash して初回 commit 1 本にする。**本体リポについてはこれで足りるので、**開発中の commit を綺麗に保つ努力は不要。**

ただし効く範囲が分かれる。

| いつ | history 消し |
|---|---|
| **public に push する前** | **完全に効く。**好きなだけ書き換えてよい |
| **一度 public に push した後** | **効かない。**fork に残り、force-push 後も SHA 直指定で dangling commit が取れる |

**運用は「常に綺麗に保つ」ではなく「公開する瞬間までに 1 回掃除する」。**

**この方針が C10 を弱めるわけではない。**history を消せるのは**本体リポだけ**で、証跡リポには使えない（D3 参照）。混在させると、消せない側に消したいものが入る。

### C40: 「アプリを起動する」を語彙に入れる。**行き先はシートに書いてあるものだけ**（2026-09-04）

2026-09-02 の実行記録（`runs/20260902-192058/run.json`）は **5 件とも `BLOCKED`** だった。
理由は端末側ではなく、**語彙にタップと入力しかなかったこと**。実物の検証シートは、
ほぼ必ず 1 行目が「アプリを起動する」で始まる。**どのシートを持ってきても 1 件目で止まる**状態だった。

- `アプリを起動する` → シートの見出し `# 対象:` が宣言したものを起動する
- `「com.example.app」を起動する` → 書いてあるものを起動する
- `設定を起動する` → **保留。**表示名からパッケージを当てにいかない

**当てにいかない理由。**「設定」がどのパッケージかは端末と地域で変わる。当てて別のアプリを
起動すると、画面は動くので通ったように見え、**間違いに気づけない**（`steps.ts` の元からの方針と同じ）。

端末側では `cmd package resolve-activity --brief` で在否を確かめてから `am start` する。
`monkey` は無いパッケージでも終了コード 0 を返すので使わない。

- **これを止めるべき条件**: シートの書き手が `# 対象:` にパッケージ名を書くことを嫌がるとき。
  そのときは「起動は人がやる」に倒す（保留になるだけで、証跡は壊れない）

### C41: 画面が追いつくのを待つ。**待つ長さではなく、結果を見て決める**（2026-09-04）

配っているシートを実機に当てたところ、5 件目（検索欄への入力）だけが落ちた。
**送った文字が黙って捨てられていた。**画面が切り替わった直後は、入力先がまだ受け取れる状態にない。

実測（エミュレータ・2026-09-04）: 0.2 秒 → 入らない / 0.5 秒 → 入らない / 1.0 秒 → 入る。

**固定の待ち時間で決め打ちしない。**端末が変わった瞬間に破れるため。3 つ入れた。

| 入れたもの | 何をするか |
|---|---|
| 操作のあとの間（既定 500ms） | 押した直後の画面は、まだ前の画面 |
| 要素が出るまで探し直す（既定 3 秒ぶん） | 1 回見て無いことを「無い」にしない。**待っても出なければ見つからないと言う** |
| 入力が入ったかを見て、**1 回だけ**送り直す | 入っていなければもう一度。**繰り返さない**（伏せ字の欄で何度も打ち込むことになる） |

**入らないまま終わっても落とさない。**入れても画面に出ない欄がある。入ったかどうかは、
このあと期待結果を見るところで判断される。

- **これを止めるべき条件**: 送り直しが二重入力を生む欄が実際に見つかったとき。
  そのときは送り直しを外し、待つ時間を端末ごとの設定にする

### C42: macOS では、使用目的を書き、署名を固定する（2026-09-04）

別プロダクト（warifu）で「許可のダイアログがたびたび出る」「カメラが動かない」という報告があり、
原因が 2 つに切り分けられた。**git-qa も同じ 2 つを踏んでいた。**

1. **`Info.plist` がそもそも無かった。**macOS は使用目的の記述が無いアプリに資源を渡さない。
   git-qa が踏む場所はファイル欄で、Finder 起動時にホームの下から検証シートを探すところ。
   **記述が無いと 0 件になる** — 「検証シートが選べない」が別の理由でまた起きていた
2. **署名が ad-hoc だった。**macOS は署名でアプリを見分けて許可を覚える。
   ad-hoc は建て直すたびに別物になるので、そのたびに聞き直される

書くのは**使うものだけ**（書類 / デスクトップ / ダウンロード）。カメラ・マイクは使わないので書かない。
ローカルネットワークも、待ち受けが 127.0.0.1 だけなので要らない。

**署名は人が行う**（§14 / §25 — 証明書の名前には個人名が入る）。手順は `docs/macos-packaging.md`。

- **これを止めるべき条件**: 待ち受けを 0.0.0.0 へ広げるとき。
  そのときは記述を足す前に、**なぜ広げるのかを決め直す**（C33 の前提が変わる）
